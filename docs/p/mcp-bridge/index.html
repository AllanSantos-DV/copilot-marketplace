mcp-bridge

v0.2.5

Onde o MCP é bloqueado por política mas extensões são permitidas, o mcp-bridge reabre a porta: conecta a servidores MCP (stdio, http, sse — com login OAuth) e entrega as tools, prompts e resources deles nativamente ao agente, com reconexão, auditoria e um painel de saúde. E um motor que já roda na sua máquina entra pelo campo engine, só pelo nome: endereço e credencial são resolvidos na hora da conexão, nunca guardados no config.

código↗

  • MCP onde a política bloqueia

    Reconecta o agente a servidores MCP pelo canal de extensões — o que a política permite — e expõe tools, prompts e resources como capacidades nativas.

  • O config guarda nome, não segredo

  • Falha alto, nunca no escuro

    Motor parado ou ausente derruba aquele servidor com erro explícito. E entrada de config que a ponte não entende aparece como aviso na sessão — nunca some calada, levando as tools junto. Erro claro agora vale mais que erro silencioso depois.

  • Tudo à vista

    Painel de saúde no app, auditoria linha a linha de cada chamada, perfis de servidores, retry com circuit breaker e limite de resposta.

#O que é

O mcp-bridge fala Model Context Protocol por baixo e reapresenta cada servidor MCP como capacidade nativa do agente: as tools viram tools dele, os prompts viram prompts, os resources viram resources. É a saída para ambientes onde o MCP direto está barrado por política, mas extensões são liberadas.

Ele não força nada — usa o canal que já é permitido para reconectar o agente a servidores que você controla, e registra cada chamada num log que dá para consultar de dentro da sessão.

i

Toda a configuração mora num arquivo só: ~/.copilot/mcp-bridge/config.json. Ele nasce na primeira sessão, já com um servidor de exemplo desligado.

#Como usar

  1. Instale o plugin

    Pelo marketplace (comando na seção Instalar) e reinicie o app uma vez — o painel entra no próximo boot.

  2. Declare seus servidores

    Abra o config.json e liste o que quer conectar: stdio para processos locais, http ou sse para os remotos.

  3. Aponte pelo motor, quando houver um

    Num servidor http/sse, troque url e headers pelo campo engine com o nome do motor. A ponte resolve endereço e credencial sozinha.

  4. Entre nos que pedem login

    mcpbridge_login <servidor> abre o navegador para autorizar (OAuth 2.1). Depois, rode /clear ou reinicie a sessão.

  5. Use as capacidades

    As tools, prompts e resources passam a aparecer nativamente para o agente. mcpbridge_list_servers mostra o que conectou e o que cada servidor trouxe.

  6. Acompanhe a saúde

    O painel MCP Bridge — Dashboard mostra status, latência e erros; mcpbridge_audit lista as últimas chamadas.

i

Mexeu no config.json? A mudança entra no próximo /clear ou reinício da sessão.

#Motor em vez de URL

Um motor é um daemon que já roda na sua máquina e anuncia onde está — o caso da ponte é o mcp-gateway, que conecta uma vez em cada servidor MCP e reexpõe tudo num endpoint só. O jeito óbvio de alcançá-lo seria colar no config a porta e o bearer dele: segredo em texto puro, num arquivo que qualquer processo com acesso ao seu HOME consegue ler.

// endereço chumbado + segredo em texto puro no seu config
{
  "name": "gateway",
  "type": "http",
  "url": "http://127.0.0.1:8765/mcp",
  "headers": { "Authorization": "Bearer <o segredo do motor, aqui>" },
  "enabled": true
}

No lugar disso, declare o nome do motor. O config passa a guardar uma referência, não uma credencial:

{
  "name": "gateway",
  "type": "http",
  "engine": "mcp-gateway",
  "enabled": true
}

Na hora de conectar, a ponte lê ~/.mcp-gateway/runtime.json para saber host, porta e caminho, e pega o bearer no cofre do motor (~/.mcp-gateway/auth-token, com ACL só do dono). Monta a conexão em memória e segue: o segredo nunca é persistido pela ponte, e a porta acompanha o motor se ele mudar.

  • engine vence url. Se os dois estiverem no mesmo servidor, quem decide é o motor vivo — uma URL velha esquecida no config não ganha dele.
  • Motor parado ou ausente falha alto. Só aquele servidor cai, com o erro dizendo o arquivo que faltou (~/.<motor>/runtime.json) e as duas saídas: subir o motor ou voltar para uma url explícita. Os demais conectam normalmente.
  • Sem fallback silencioso. Adivinhar uma porta, ou conectar sem o bearer, trocaria um erro claro agora por um erro obscuro no meio do trabalho.
  • A ponte não instala motor. Ela só usa o que já está na máquina: instalar e atualizar continuam sendo ação explícita sua, e o bootstrap do plugin é offline — não baixa nem executa código remoto, requisito do ambiente onde esta ponte existe.
i

Conferido nesta versão: 8/8 no harness do engine — motor ausente, precedência sobre url, motor sem token, runtime.json corrompido e url literal intacta — mais 72/72 no gate de qualidade e 4/4 na verificação de instalação ponta a ponta.

#Servidores e ajustes

Um config.json, um objeto por servidor. Os transportes:

  • stdio — processos MCP locais, com command, args, env e cwd.
  • http e sse — servidores remotos, por url explícita ou pelo nome do motor em engine.
  • OAuth 2.1 — para quem exige login: fluxo com PKCE e registro dinâmico de cliente. mcpbridge_login abre o navegador; mcpbridge_logout apaga os tokens salvos.

E os ajustes que impedem um servidor ruim de estragar a sessão:

  • Perfis — conjuntos nomeados de servidores (dev, prod); mcpbridge_use_profile troca o ativo e persiste a escolha.
  • Resiliência — retry com backoff e circuit breaker por servidor: quem está caindo é isolado em vez de arrastar todo mundo.
  • Limite de resposta — resposta gigante é truncada ou paginada, com aviso, para não estourar o contexto do agente.
  • Timeouts — um para abrir a conexão, outro por chamada de tool.
  • Auditoria — cada chamada vira uma linha em ~/.copilot/mcp-bridge/audit.jsonl, com opção de ocultar os argumentos.

#Painel e auditoria

A ponte registra o painel MCP Bridge — Dashboard no app: a foto do que está de pé — servidor, transporte, status, quantas tools, prompts e resources cada um trouxe, latência média, erros e as últimas chamadas auditadas. E a foto não congela no boot: quando um servidor avisa que mexeu nas próprias tools (notifications/tools/list_changed), a ponte relê o catálogo dele e atualiza o que mostra.

As mesmas respostas vêm por tools, sem sair do chat:

  • mcpbridge_list_servers — o diagnóstico da ponte: status, erro da última tentativa e o que cada servidor expôs.
  • mcpbridge_audit — as últimas chamadas (servidor/tool, status, duração), com filtro por servidor ou tool.
  • mcpbridge_profiles e mcpbridge_use_profile — vê e troca o perfil ativo.
  • mcpbridge_login e mcpbridge_logout — entra e sai dos servidores com OAuth.
  • mcpbridge_list_resources e mcpbridge_read_resource — lista e lê os resources dos servidores conectados.

No início de cada sessão a ponte anuncia quantos servidores conectaram e quantas capacidades entraram. Se algum falhou, o aviso nomeia o servidor e o motivo — em vez de sumir com ele da lista.

!

A lista de tools que o agente enxerga é montada uma vez, na abertura da sessão. Uma tool que nasceu depois disso aparece na hora para você — no painel e no mcpbridge_list_servers —, mas só chega ao agente no próximo /clear ou reinício da sessão.

#Estrutura

Runtime vendado em plugins/mcp-bridge/ — vem do repositório de origem, então não se edita à mão aqui. É isto que o copilot plugin install entrega:

⌁ plugins/mcp-bridge/
  • boot.mjs Bootstrap de SessionStart offline: roda o sync.mjs vendado aqui — não baixa nem executa código remoto. 1.1 KB
  • boot.neural-link.json Calibragem do SessionStart entregue ao dispatcher: o plugin não declara hook próprio. 353 B
  • extension.mjs A ponte: conecta os servidores do config, resolve o motor pelo nome, expõe tools/prompts/resources ao agente e abre o painel. 765 KB

#Perguntas frequentes

Isso burla a política da empresa?

Não força nada: usa o canal de extensões, que a política já permite, para reconectar o agente a servidores MCP que você controla — e registra cada chamada em ~/.copilot/mcp-bridge/audit.jsonl, com o painel mostrando o que está conectado.

O que é um “motor” aqui?

Um daemon local que anuncia onde está num runtime.json dentro do seu HOME (~/.<motor>/) — o mesmo padrão do vox-engine e da embed-house desta vitrine. Para a ponte, o motor da vez é o mcp-gateway: ele conecta uma vez em cada servidor MCP e reexpõe tudo num endpoint só.

O plugin instala o motor para mim?

Não, e é de propósito: a ponte só usa um motor que já está na máquina. Instalar ou atualizar continua sendo ação explícita sua — o bootstrap do plugin é offline e não baixa nem executa código remoto, porque esta ponte roda justamente onde isso não é aceitável.

E se o motor estiver parado?

Aquele servidor falha com erro explícito, dizendo o arquivo que faltou (~/.<motor>/runtime.json) e as duas saídas: subir o motor ou trocar para uma url explícita. Os outros servidores conectam normalmente — a ponte não adivinha porta nem tenta conectar sem credencial.

Posso continuar usando url e headers?

Pode. Uma url explícita continua valendo exatamente como você escreveu; o campo engine só entra quando você o declara. Se os dois aparecerem no mesmo servidor, o motor vivo vence — para que um endereço velho no config não sequestre a conexão.

Meu token fica salvo no config?

Não. Com engine, a ponte lê o bearer do cofre do motor na hora de conectar e o usa em memória — nada é gravado no config.json. Os tokens de OAuth ficam à parte, em ~/.copilot/mcp-bridge/oauth/, com permissão restrita ao seu usuário.

Que transportes suporta?

stdio para processos locais, http e sse para remotos — com login OAuth 2.1 (PKCE e registro dinâmico de cliente) quando o servidor exige.
